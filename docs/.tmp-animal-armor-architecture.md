# Temporary architecture plan: animal armor infusions

Status: temporary working document. Delete before merging to `main`.

## Current-system analysis

Alchemical Leather currently has four tightly coupled assumptions:

1. `Infusions.slot(ItemStack)` recognizes only the four vanilla humanoid leather pieces.
2. `EffectSlotRules` maps effects only to HEAD/CHEST/LEGS/FEET and `Infusions.resolve` rejects any effect without such a mapping.
3. `EquipmentInfusions` and entity equipment listeners inspect only those four humanoid slots.
4. The cauldron path therefore cannot infuse or activate `EquipmentSlot.BODY` items, even though the component/ledger machinery itself is entity-generic.

The cauldron already stores complete `PotionContents`, so it can preserve multi-effect potions without a block-entity format change. `EffectLedger` already manages arbitrary effect identifiers independently and can remain the single projected armor source per effect while animal-bundle clocks live on the item.

## Requested behavior

- Vanilla leather horse armor and wolf armor can be infused.
- Animal armor is not constrained by the humanoid effect-to-slot table: it can carry every potion that contains at least one effect, including multi-effect potions.
- Normal and splash potion effects retain their individual durations and pause while the armor is not equipped.
- Lingering potion effects remain stable/infinite while the armor is equipped.
- Instant effects fire once when the infused armor is equipped and are then consumed from that infusion; other effects in the same animal infusion remain.
- Existing enchantment mutual exclusion, dye color, washing, repair safeguards, serialization and external-effect ownership semantics remain intact.
- A mod-added leather animal armor should inherit the feature automatically when it is a BODY-slot equippable and exposes normal leather semantics.

## Classification architecture

Introduce one centralized classification path in `Infusions`:

- Humanoid leather: keep the existing exact four vanilla pieces and their HEAD/CHEST/LEGS/FEET mapping.
- Animal-compatible armor: require `DataComponents.EQUIPPABLE.slot() == EquipmentSlot.BODY`, then accept when either:
  - the item is in `#alchemical_leather:animal_armor` (the built-in tag contains vanilla wolf armor), or
  - the item uses the vanilla leather equipment asset, or
  - its `DataComponents.REPAIRABLE` accepts vanilla leather as a repair ingredient.

This makes ordinary modded BODY armor built from the vanilla leather material or repaired with leather work automatically, while avoiding accidental support for metal horse/nautilus armor, carpets or harnesses. The item tag is an explicit extension point for unusual modded animal armor whose implementation does not expose those normal leather properties.

Centralize target authorization as `Infusions.accepts(stack, actualSlot, effectId)`: BODY animal armor accepts every stored effect; humanoid leather still requires `EffectSlotRules.slot(effectId) == actualSlot`.

## Potion-resolution architecture

Split potion parsing from humanoid slot policy:

- `resolveAll(PotionContents, bottleItem)` validates that potion contents exist and contain at least one effect, then converts every effect instance to an `Infusion` payload using the existing timed/stable/instant rules. It does not consult `EffectSlotRules` and preserves repeated effect IDs as separate timed sources.
- The legacy/single resolution path remains for humanoid armor and requires exactly one effect plus a registered humanoid slot rule.
- Filling a potion cauldron uses `resolveAll`, because a potion unsupported by humanoid armor may still be valid for animal armor.
- Infusing humanoid armor uses the single/policy-constrained path.
- Infusing animal armor stores the full resolved effect list.

Water, mundane/thick or otherwise effectless contents remain non-infusible because they carry no effect to apply.

## Data model

Preserve the existing `alchemical_leather:infusion` component for humanoid items and backwards compatibility.

Add `alchemical_leather:animal_infusion`, represented by a small record containing a non-empty list of `Infusion` values. Give it persistent and network codecs. The list may contain repeated effect IDs because custom `PotionContents` can legally do so. This avoids changing the on-disk shape of existing alpha.1 infused armor while allowing one animal item to own several potion effects.

`Infusions.blocked` becomes true for either component. Washing removes either component. Tooltip rendering supports both, listing each effect and its timing. Human items continue to use the old component unchanged.

## Runtime synchronization

Expand watched equipment slots to include `EquipmentSlot.BODY`.

Refactor `EquipmentInfusions` so each equipped supported stack yields zero or more `Infusion` entries:

- humanoid item: one legacy infusion;
- animal item: the list from `animal_infusion`.

For each equipped animal bundle:

1. Consume each instantaneous entry immediately before executing it, so death/removal during the effect cannot replay an already-fired instant source.
2. Group non-instant entries by effect identifier for projection only.
3. For repeated entries of the same effect, project the currently strongest source using the same amplifier-then-duration/infinite priority already used by `EffectLedger`; all underlying animal timed sources still keep independent clocks.
4. Let `EffectLedger` arbitrate that projected armor winner against external vanilla effects exactly as it does today.
5. After the entity effect tick, decrement every equipped animal `timed` entry by one independently, remove expired entries, and replace/remove the item component accordingly. Stable entries do not decrement.

This parallel clocking means a shorter stronger repeated source can expire and reveal a weaker longer source later, rather than losing the hidden source. Humanoid armor continues using the existing ledger-backed clock writeback path.

`EffectLedger` itself should not need architectural changes.

## Cauldron transaction rules

Keep mutation atomicity: validate potion, target classification, enchantments and target authorization before consuming a cauldron dose or replacing an item stack.

Animal infusion should copy the original stack, preserve unrelated components, set the potion color, remove any legacy single infusion, and replace any prior animal bundle rather than combining old and new potions. Humanoid infusion symmetrically removes any animal bundle. Reinfusion is replacement, not accumulation.

## Compatibility and extensibility

No compile-time dependency on Clinging Reoriented, Alex's Mobs or any third-party animal-armor mod. Effect identifiers remain runtime-resolved by the existing registry logic.

Clinging/Reorientation therefore work on animal armor because animal armor has no effect-slot restriction, not because of special-case code.

The BODY/leather classifier plus opt-in item tag is the compatibility boundary for future animal armor.

## Architectural invariants

- Existing alpha.1 humanoid infusion data remains decodable.
- Human slot restrictions do not loosen.
- Animal BODY armor never depends on effect-slot datapack mappings.
- Unsupported/non-animal BODY equipment is not made infusible merely because it occupies BODY.
- Repeated custom potion effects do not overwrite or freeze one another's clocks.
- External potion/effect ownership semantics remain separated from armor clocks.
- No global entity or inventory scan is introduced.
