# Temporary architecture plan: animal armor infusions

Status: temporary working document. Delete before merging to `main`.

## Current-system analysis

Alchemical Leather currently has four tightly coupled assumptions:

1. `Infusions.slot(ItemStack)` recognizes only the four vanilla humanoid leather pieces.
2. `EffectSlotRules` maps effects only to HEAD/CHEST/LEGS/FEET and `Infusions.resolve` rejects any effect without such a mapping.
3. `EquipmentInfusions` and entity equipment listeners inspect only those four humanoid slots.
4. The cauldron path therefore cannot infuse or activate `EquipmentSlot.BODY` items, even though the component/ledger machinery itself is entity-generic.

The cauldron already stores complete `PotionContents`, so it can preserve multi-effect potions without a block-entity format change. `EffectLedger` already manages arbitrary effect identifiers independently and can remain the single projected armor source per effect while animal-bundle clocks live on the item.

## Requested behavior

- Vanilla leather horse armor and wolf armor can be infused.
- An animal armor carries exactly **one potion infusion at a time**. Reinfusing replaces that potion; different potions are never accumulated on one armor item.
- One potion may itself contain several effects (for example Turtle Master); all effects belonging to that one potion are retained together.
- Animal armor is not constrained by the humanoid effect-to-slot table: the one stored potion may be any effectful potion.
- Normal and splash potion effects retain their individual durations and pause while the armor is not equipped.
- Lingering potion effects remain stable/infinite while equipped.
- Instant effects fire once when the infused armor is equipped and are then consumed from that potion infusion; non-instant sibling effects from the same potion remain.
- Existing enchantment mutual exclusion, dye color, washing, repair safeguards, serialization and external-effect ownership semantics remain intact.
- Compatibility is based on **dyeability, not leather material**: a mod-added dyeable animal armor should inherit the feature automatically when it uses standard Minecraft dyeing semantics.

## Classification architecture

Keep humanoid behavior unchanged: the exact four vanilla leather pieces continue to map to HEAD/CHEST/LEGS/FEET and use the effect-slot datapack table.

For animal armor, introduce a server-data reload index of items that are dyeable under the standard Minecraft item-color system:

- scan loaded `data/*/recipe/**/*.json` resources during server-data reload;
- collect targets of recipes whose type is `minecraft:crafting_dye`;
- support ordinary item targets plus tag/array ingredient forms where representable from recipe JSON;
- cache item IDs and target item tags rather than scanning recipes during gameplay.

An item is animal-infusion-compatible when:

1. its `DataComponents.EQUIPPABLE` slot is `EquipmentSlot.BODY`; and
2. it is known by that dyeability index, or is explicitly listed/tagged by the Alchemical Leather extension point described below.

This intentionally keys off the **actual dye recipe mechanic**, not leather repair material or a hard-coded equipment asset. Vanilla leather horse armor and wolf armor both use `minecraft:crafting_dye`, so they qualify naturally. A modded BODY armor using the same standard dye-recipe type qualifies without Alchemical Leather knowing its item ID.

Provide `#alchemical_leather:dyeable_animal_armor` as a compatibility extension point for mods whose armor is genuinely dyeable but implements dyeing through a non-standard/custom recipe or interaction. The tag is a fallback, not the primary automatic path.

Centralize target authorization as `Infusions.accepts(stack, actualSlot, effectId)`: compatible BODY armor accepts every stored effect; humanoid leather still requires `EffectSlotRules.slot(effectId) == actualSlot`.

## Potion-resolution architecture

Split potion parsing from humanoid slot policy:

- `resolveAll(PotionContents, bottleItem)` validates that potion contents exist and contain at least one effect, then converts every effect instance to an `Infusion` payload using timed/stable/instant rules. It does not consult `EffectSlotRules` and preserves repeated effect IDs as separate timed sources.
- The legacy/single resolution path remains for humanoid armor and requires exactly one effect plus a registered humanoid slot rule.
- Filling a potion cauldron uses `resolveAll`, because a potion unsupported by humanoid armor may still be valid for animal armor.
- Infusing humanoid armor uses the single/policy-constrained path.
- Infusing animal armor stores one `AnimalInfusion` bundle representing **one potion**, containing all effects supplied by that potion.

Water, mundane/thick or otherwise effectless contents remain non-infusible because they carry no effect to apply.

## Data model

Preserve the existing `alchemical_leather:infusion` component for humanoid items and backwards compatibility.

Add `alchemical_leather:animal_infusion`, represented by a record containing a non-empty list of `Infusion` values. Semantically the record is **one potion infusion**, not a bag into which independent potions can be appended. Its list exists only because one potion can contain multiple effect instances. The list may contain repeated effect IDs because custom `PotionContents` can legally do so.

`Infusions.blocked` becomes true for either component. Washing removes either component. Tooltip rendering supports both, listing the effects of the one stored potion. Human items continue to use the old component unchanged.

## Runtime synchronization

Expand watched equipment slots to include `EquipmentSlot.BODY`.

Refactor `EquipmentInfusions` so each equipped supported stack yields zero or more effect entries from its single stored infusion:

- humanoid item: one legacy effect;
- animal item: all effect entries belonging to its one `animal_infusion` potion bundle.

For each equipped animal bundle:

1. Consume each instantaneous entry immediately before executing it, so death/removal during the effect cannot replay an already-fired instant source.
2. Group non-instant entries by effect identifier for projection only.
3. For repeated entries of the same effect, project the currently strongest source using the same amplifier-then-duration/infinite priority already used by `EffectLedger`; all underlying timed sources still keep independent clocks.
4. Let `EffectLedger` arbitrate that projected armor winner against external vanilla effects exactly as it does today.
5. After the entity effect tick, decrement every equipped animal `timed` entry by one independently, remove expired entries, and replace/remove the item component accordingly. Stable entries do not decrement.

This parallel clocking means a shorter stronger repeated source can expire and reveal a weaker longer source later, rather than losing the hidden source. Humanoid armor continues using the existing ledger-backed clock writeback path.

`EffectLedger` itself should not need architectural changes.

## Cauldron transaction rules

Keep mutation atomicity: validate potion, target classification, enchantments and target authorization before consuming a cauldron dose or replacing an item stack.

Animal infusion copies the original stack, preserves unrelated components, sets the potion color, removes any legacy single infusion, and **replaces** any previous animal potion bundle. It never merges two separate potions. Humanoid infusion symmetrically removes any animal bundle.

## Compatibility and extensibility

No compile-time dependency on Clinging Reoriented, Alex's Mobs or third-party animal-armor mods. Effect identifiers remain runtime-resolved by the existing registry logic.

Clinging/Reorientation work on compatible animal armor because BODY animal armor has no effect-slot restriction, not because of special-case effect code.

The automatic compatibility boundary is standard `minecraft:crafting_dye` semantics plus BODY equipment. `#alchemical_leather:dyeable_animal_armor` covers custom dye systems that cannot be inferred generically from server data.

## Architectural invariants

- Existing alpha.1 humanoid infusion data remains decodable.
- Human slot restrictions do not loosen.
- An animal armor contains at most one potion infusion; its multiple entries can only be effects from that one potion.
- Animal BODY armor never depends on effect-slot datapack mappings.
- BODY equipment is not made infusible merely for being leather, repairable with leather, or occupying BODY.
- Standard dyeable modded BODY armor is discovered from loaded recipes without per-item integration code.
- Repeated custom potion effects do not overwrite or freeze one another's clocks.
- External potion/effect ownership semantics remain separated from armor clocks.
- No global entity or inventory scan is introduced.
