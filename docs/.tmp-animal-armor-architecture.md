# Temporary architecture plan: dyeable armor infusions

Status: temporary working document. Delete before merging to `main`.

## Scope and invariants

Alchemical Leather alpha.1 is limited to the four vanilla humanoid leather pieces, does not inspect `EquipmentSlot.BODY`, rejects multi-effect potions, and relies on optional BedrockIfy support for colored-water dyeing. The target release generalizes the feature to genuinely dyeable armor, adds animal armor, and makes the full dye/infuse/wash loop native.

Hard invariants:

- Eligibility is based on dyeability plus an actual armor equipment slot, never merely leather material, repair material, item ID or renderer asset.
- HUMANOID_ARMOR keeps the existing effect-to-body-part table and one-effect component format.
- ANIMAL_ARMOR/BODY accepts any effectful potion, but one armor item stores exactly one potion at a time. A single potion may contain several or repeated effect entries.
- Existing alpha.1 `alchemical_leather:infusion` data remains decodable.
- External vanilla effects remain independent from armor-owned clocks.
- Timed armor effects advance only while equipped; lingering is stable; instant effects fire once.
- Enchanting and infusion remain mutually exclusive.
- Native dyed-water functionality works without BedrockIfy; installing BedrockIfy must never double-consume dye or fluid.
- No global inventory/entity scans.

## Dyeability classifier

A stack is dyeable when at least one standard/custom signal is true:

1. it belongs to `#minecraft:cauldron_can_remove_dye`;
2. it is the **self-recoloring result** of a loaded `minecraft:crafting_dye` recipe; or
3. it belongs to `#alchemical_leather:dyeable_armor`, the fallback for custom dye systems.

`crafting_dye` recipes are indexed on server-data reload. The result item must also be accepted by its own target ingredient:

- direct target: target ID must equal result ID;
- list target: only the result is indexed, and only if the list contains that result ID;
- tag target: cache `(result ID, target tag)` and require both that exact result ID and runtime membership in the tag.

“Loaded recipe” is deliberately defined by Minecraft/Fabric semantics rather than by the mere presence of a JSON file. The index therefore receives the reload registry context, evaluates `fabric:load_conditions`, validates each surviving candidate through Minecraft 26.2's `DyeRecipe.MAP_CODEC`, and only then extracts the minimal target/result structure needed for self-recoloring classification. A conditionally disabled or codec-invalid recipe contributes no dyeability evidence. Broken/unparseable recipe resources are ignored by this auxiliary index rather than causing Alchemical Leather to fail the whole datapack reload, matching the recipe manager's fail-local behavior.

Other inputs of a transmuting recipe never become dyeable merely because the recipe produces a dyed item. This prevents A→B dye recipes from falsely classifying A as in-place recolorable.

`Infusions.slot(stack)` then requires `DataComponents.EQUIPPABLE`, `slot().isArmor()` and exact dyeability. `Infusions.accepts(stack, slot, effect)` applies:

- `HUMANOID_ARMOR`: `EffectSlotRules.slot(effect) == slot`;
- `ANIMAL_ARMOR`: any valid effect.

Exact dyeability remains server-authoritative. Client interaction prediction uses only broad `armorCandidate(stack)` (`EQUIPPABLE` + armor slot) so remote clients do not need a duplicate server recipe index.

## Potion model

`resolveAll(PotionContents, bottleItem)` converts every effect instance into an `Infusion`, preserving repeated IDs. Normal/splash effects are timed, lingering effects are stable and instantaneous effects are instant.

The legacy `resolve` path remains for humanoid armor and requires exactly one effect plus a slot rule. Potion cauldrons themselves accept any effectful potion because BODY armor can use effects that have no humanoid mapping.

Humanoid items keep `alchemical_leather:infusion`. BODY items use `alchemical_leather:animal_infusion`, a non-empty list that semantically represents **one potion bundle**, not an accumulator for separate potions. Reinfusion replaces the previous bundle.

## Runtime ownership and clocks

Watch HEAD/CHEST/LEGS/FEET/BODY.

- Humanoid armor uses the existing single-source ledger path.
- BODY projects all non-instant entries from its one potion bundle.
- Instant BODY entries are removed before firing so death/removal cannot replay them.
- Repeated entries of one effect retain independent clocks; only the strongest active source is projected.
- Expiring a stronger repeated source immediately reveals a surviving weaker source without a blank tick.
- Unequipping pauses item clocks and removes only armor-owned projected effects.
- `EffectLedger` continues to arbitrate armor projections against external vanilla effects.

### ServerPlayer connection lifecycle

Equipment-change and entity-load callbacks can run while a `ServerPlayer` is being constructed/loaded but before `ServerPlayer.connection` exists. Projecting an effect then calls `ServerPlayer.onEffectAdded`, which attempts to send a packet and crashes with the user-visible login failure reported as invalid player data.

Therefore `EquipmentInfusions.sync` must treat an unconnected `ServerPlayer` as a deferred state:

- if `entity instanceof ServerPlayer` and `connection == null`, return **before** creating/projecting a ledger, consuming instant entries or advancing any armor clock;
- register `ServerPlayConnectionEvents.JOIN` and call `EquipmentInfusions.sync(handler.player)` once the play connection is established;
- the JOIN reconciliation becomes the guaranteed projection point for armor already loaded before networking was ready.

This guard applies equally to humanoid and BODY infusions. It fixes lifecycle safety without weakening effect semantics or silently losing instant effects during load.

## Native dyed-water cauldron

`alchemical_leather:dyed_water_cauldron` stores six logical fluid units plus RGB in a synchronized block entity. Logical levels map to vanilla visuals: 1-2 → water level 1, 3-4 → level 2, 5-6 → full.

Volume rules intentionally match BedrockIfy granularity:

- vanilla water 1/2/3 + first dye → dyed water 2/4/6;
- dye one armor item → consume 1 unit;
- glass bottle → require/consume 2 units, return ordinary water potion;
- empty bucket → require level 6, return water bucket and empty;
- water potion at `n < 6` → strip tint and create vanilla water `min(floor(n/2)+1, 3)`; level 6 is already full and consumes nothing;
- water bucket refill is delegated to the block's vanilla EMPTY dispatcher, which strips tint and creates full vanilla water.

Dyes are recognized through `DataComponents.DYE`. Additional dye blends RGB with Minecraft/BedrockIfy brightness-preserving semantics and does not change fluid amount; a no-op blend consumes no dye.

Dyeing qualifying armor from native colored water blends with existing `DYED_COLOR`, preserves infusion and unrelated components, and consumes one unit. Vanilla water washing removes `DYED_COLOR`, `infusion` and `animal_infusion` and consumes one vanilla water level, including merely dyed/uninfused qualifying armor.

## BedrockIfy coexistence

Ownership is per entry point rather than feature-wide disablement:

1. Alchemical Leather always owns its own dyed-water block.
2. BedrockIfy owns its potion/colored-water blocks; Alchemical Leather intercepts only its armor-specific compatibility actions there and returns success after handling them. Ordinary potion-bottle lifecycle on BedrockIfy potion cauldrons remains entirely BedrockIfy's responsibility.
3. For **vanilla water + dye**, Alchemical Leather yields only when BedrockIfy colored-water blocks are registered and reflective `Bedrockify.getInstance().settings.bedrockCauldron` is true. If absent, disabled or unverifiable for any reflective/linkage/runtime reason, Alchemical Leather creates its native dyed water.
4. Alchemical Leather remains responsible for washing its own infusion components from qualifying armor in vanilla water.

BedrockIfy colored-water compatibility blends existing item color and consumes exactly one of its six units. BedrockIfy potion compatibility consumes exactly one canonical potion dose without replacing BedrockIfy's block. No compile-time BedrockIfy dependency, registry replacement, handler clearing, mixin-priority trick or production settings mutation is introduced.

## Atomic transactions

Validate exact armor eligibility, potion/effect policy, enchantments and source state before consuming dye/fluid or replacing a stack. Potion infusion sets potion color; recoloring preserves infusion; vanilla water removes color and both infusion formats. Unsupported/rejected interactions do not consume cauldron contents.

## Validation and release sequence

Adversarial tests must cover classification signals and false positives, Fabric load conditions and invalid-recipe rejection, humanoid/BODY policy, one-potion replacement, multi/repeated/instant effects, pause/resume, external ownership, serialization, native six-level dyed water, BedrockIfy ownership handoff, real Clinging alpha.6 integration, client synchronization and the pre-connection ServerPlayer regression.

After two consecutive review passes produce no changes: update permanent docs and mod metadata, bump to `0.1.0-alpha.2`, delete temporary plans, run final CI, merge to `main`, verify merged CI, create `v0.1.0-alpha.2` prerelease matching alpha.1 style, then update Clinging Reoriented README so animal-armor support is described as current.
