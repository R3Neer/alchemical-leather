# Temporary implementation checklist: dyeable armor infusions

Status: temporary working document. Delete before merging to `main`.

## Data model and classification

- [x] Preserve the existing `alchemical_leather:infusion` component format for backwards-compatible humanoid armor.
- [x] Add `AnimalInfusion` and `alchemical_leather:animal_infusion` as one non-empty potion bundle for BODY armor.
- [x] Add `#alchemical_leather:dyeable_armor` as the fallback for non-standard custom dye systems.
- [x] Treat `#minecraft:cauldron_can_remove_dye` as a first-class standard dyeability signal.
- [x] Tighten `minecraft:crafting_dye` discovery so only an output item that is also accepted by its own target ingredient is considered self-recolorable.
- [x] For direct target recipes require target ID == result ID; for list targets require the result ID to be in the list; for tag targets cache `(result, targetTag)` and verify runtime membership.
- [x] Explicitly reject non-result inputs of transmuting `crafting_dye` recipes as dyeability evidence.
- [x] Keep server-data indexing rather than runtime recipe scans.
- [x] Generalize `Infusions.slot` to dyeable `EQUIPPABLE` items whose slot `isArmor()`, covering HUMANOID_ARMOR and ANIMAL_ARMOR.
- [x] Remove leather asset/repairability heuristics completely.
- [x] Add broad `armorCandidate(stack)` only for client interaction prediction; keep exact dyeability server-authoritative.
- [x] Watch HEAD/CHEST/LEGS/FEET/BODY and make `blocked` cover both infusion component types.
- [x] Keep humanoid effect-to-slot restrictions and allow any effect on ANIMAL_ARMOR.
